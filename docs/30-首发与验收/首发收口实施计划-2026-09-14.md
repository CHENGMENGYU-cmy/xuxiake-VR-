## 1. 目标

把当前项目从“本机演示可看、部分功能已做”收敛到“可以给外部用户试用的首发版本”。本计划优先修复已确认问题，不扩展新功能，不重写架构，不把历史汇报当作当前验收结果。

首发收口的完成标准：

- P0问题全部关闭，并有测试或可复现检查证明。
- 关键P1不再影响普通用户完成核心流程。
- 代码、数据库迁移、媒体资产、交接文档形成一致版本。
- 至少完成一轮端到端验收：登录、发布内容、搜索、评论、加入社群、消息或通知。
- 明确哪些内容仍是演示边界，例如视频占位、第三方登录暂未开放等。

## 2. 总体策略

先稳住账号、认证、测试和搜索，再处理登录入口、媒体交付、文档与版本，最后做完整用户流程验收。

建议不要在第一轮加入推荐算法、分享传播、真实视频素材、云审核、线上部署等扩展事项。它们不是不重要，而是会把当前未闭合的问题继续摊大。

## 4. 具体任务包

### T01 · 建立修复基线

目的：避免一边修一边丢失当前机器上已有成果。

工作内容：

- 复查当前Git状态，把代码改动、SQL、媒体、备份、本机配置分组。
- 标记哪些文件应进入版本，哪些只做本机备份。
- 确认数据库结构和服务启动状态。
- 保存一份“修复前检查记录”，但不重复执行会改数据的旧SQL。

验收：

- 有一份明确的纳入版本清单。
- 不把 `.codex/config.toml`、数据库备份、临时截图这类本机产物混进首发代码。
- `项目现状与问题清单-2026-09-14.md` 中的当前问题编号仍可追踪。

### T02 · 修复账号生命周期

目的：让注销、封禁、恢复和旧会话策略真正能执行。

工作内容：

- 扩展用户状态，至少明确 `ACTIVE`、`BANNED`、`DEACTIVATED` 的含义。
- 为注销原因、注销时间、冷静期截止时间增加专用字段，不再覆盖用户简介。
- 注销操作使用事务处理账号状态和内容可见性变化。
- 明确恢复策略：恢复账号时哪些内容恢复，哪些保持私密。
- 统一登录、刷新、已登录接口对账号状态的处理。

验收：

- 数据库迁移、实体定义和接口写入值一致。
- 注销接口在严格数据库模式下成功。
- 注销后旧token不能继续操作受保护资源。
- 冷静期恢复有明确接口或管理流程。
- 对应测试覆盖注销、恢复、重复注销、封禁用户访问。

### T03 · 修复认证与验证码边界

目的：阻止刷新令牌和访问令牌混用，避免生产环境接受固定测试验证码。

工作内容：

- 在token负载中加入用途字段，例如 `access` 和 `refresh`。
- 刷新接口只接受刷新令牌，业务接口只接受访问令牌。
- token校验时读取用户当前状态，拒绝被封禁或已注销用户。
- 密码修改、注销、封禁后的会话失效策略写入代码和测试。
- `TEST1234` 仅在明确的开发或测试配置下可用。

验收：

- 刷新令牌调用普通接口失败。
- 访问令牌调用刷新接口失败。
- 封禁、注销后旧token无法继续访问受保护接口。
- 生产配置下固定验证码无效。
- 正常验证码仍支持过期、错误次数、一次性使用。

### T04 · 恢复权限测试与社群边界

目的：把已有社群权限逻辑重新放回可靠测试基线。

工作内容：

- 补齐 `social-permissions.spec.ts` 中缺失的 `postRepo` 测试替身。
- 检查贡献统计逻辑是否影响权限判断或只是详情展示。
- 复跑后端测试，必要时补充角色边界用例。
- 复跑社群相关浏览器E2E，验证创建者、管理员、版主、成员、游客的差异。

验收：

- 后端权限测试恢复通过。
- 社群详情接口继续正常返回。
- 浏览器权限测试能覆盖主要角色按钮和接口拒绝。

### T05 · 接通真实搜索

目的：让新用户和新帖子进入搜索结果，避免页面只搜索演示数据。

工作内容：

- 后端提供或补齐用户搜索、帖子搜索接口。
- 前端搜索页和搜索建议框改为调用真实接口。
- 保留必要的空状态、加载态和错误态。
- 搜索结果遵守内容可见性：私密内容不泄露，删除或隐藏内容不残留。

验收：

- 新注册用户可被搜索到。
- 新发布公开帖子可被搜索到。
- 私密帖子、注销用户、封禁用户按策略隐藏。
- 搜索页和建议框结果一致。

### T06 · 收敛登录入口

目的：首版不把不可用入口展示成可用功能。

工作内容：

- 决定首版登录方式：账号密码、短信、微信、支付宝分别是开放、隐藏还是标记未开放。
- 如果保留短信登录，接入真实短信服务或明确仅开发环境使用控制台验证码。
- 如果不做第三方登录，隐藏微信/支付宝按钮或改成明确的暂未开放状态。
- 更新登录页文案，避免用户点了没有结果。

验收：

- 用户能通过至少一种正式方式完成注册、登录、退出、再次登录。
- 不可用入口不会给出假成功或静默无响应。
- README和交接文档与实际登录方式一致。

### T07 · 处理媒体资产交付

目的：让真实地点图片和默认头像在新环境可恢复。

工作内容：

- 确认 `server/uploads/real-covers/` 的17张真实地点图片和 `ATTRIBUTION.json` 如何交付。（2026-09-16 已完成：资产源改为 `server/assets/real-covers/`，运行时目录可由脚本恢复）
- 新用户默认头像改为本地可控资源或稳定的项目内默认图。
- 将图片SQL、媒体文件、来源清单纳入同一恢复流程。
- 保留视频占位降级，但在演示数据说明中写清楚。

验收：

- 新环境按文档恢复后，社区封面和媒体图能正常显示。
- 新注册用户头像不依赖外部随机服务。（2026-09-15 已完成）
- 来源清单与实际文件一一对应。（2026-09-16 已完成：`server/assets/real-covers/manifest.json` + `ATTRIBUTION.json`）
- 视频占位不会被误写成真实可播放视频。

### T08 · 文档、版本和验收记录收口

目的：让项目状态只保留一个当前事实入口。

工作内容：

- 更新README中过期的“任意密码”等说明。
- 更新AI_HANDOFF和项目开发交接记录，让它们指向最新问题清单和本计划。
- CHANGELOG只记录历史变化，不再承担当前验收结论。
- 根据最终修复结果生成一份带日期的首发验收记录。

验收：

- 新接手者先读最新现状、计划、验收记录即可判断项目状态。
- 历史文档不会再把旧的“8项通过”误认为当前通过。
- Git版本中包含必要代码、迁移和文档；媒体和备份有独立说明。

## 5. 首发验收清单

首发前建议至少完成以下检查：

| 检查项 | 通过标准 |
|---|---|
| 前端类型检查 | 退出码0 |
| 后端类型检查 | 退出码0 |
| 后端测试 | 与账号、认证、权限相关测试通过 |
| 前端构建 | 生产构建成功 |
| 浏览器核心流程 | 两个账号完成注册/登录、发布、搜索、评论、社群操作、消息或通知 |
| 权限边界 | 游客、普通成员、管理员、封禁/注销用户行为符合预期 |
| 媒体显示 | 社区图、帖子图、头像在页面中真实显示 |
| 数据恢复 | 新环境可按SQL和资产说明恢复 |
| 文档一致 | README、交接文档、CHANGELOG和验收记录不互相矛盾 |

## 6. 暂缓事项

以下事项建议等首发收口后再做：

- 推荐算法效果优化。
- 分享传播、邀请裂变、活动增长。
- 真实视频素材采集和上传转码。
- 云图片审核和更复杂的风控。
- 正式短信、微信、支付宝全部接入。
- 线上域名、HTTPS、备份监控和生产运维自动化。

若决定公开给外部用户长期使用，线上部署和备份监控不能再暂缓；它们应在首发验收通过后作为发布阶段单独执行。

## 7. 推荐执行顺序

若下一步由Codex继续实现，建议按以下顺序开工：

1. T01：先整理版本边界和修复前基线。
2. T02 + T03：修复账号生命周期、token和验证码，这是首发阻断项。
3. T04：恢复权限测试，让后续修改有保护网。
4. T05：接通真实搜索，补齐用户能感知的核心功能。
5. T06 + T07：收敛登录入口和媒体资产。
6. T08：同步文档与验收记录。
7. 最后执行首发验收清单，再决定是否部署或继续加功能。

我的建议是先做T01-T05。它们最能降低“明明页面有了，但一给别人用就露馅”的风险。
